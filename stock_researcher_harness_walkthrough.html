第一部分

回顾 DeepSeek Harness 核心概念

Profile · Bundle · Plugin · Context · Runtime · Agent

第一部分 · 概念

六个概念，一句话各讲清

🧠 Agent（智能体）

一轮轮循环：决定调哪个工具、读系统提示、按需加载技能。能力不写死，用 Runtime 给的那一套。

⚙️ Runtime（运行时）

把组合好的 Profile 实例化出的运行环境：一棵 Cordis Context 树 + 生命周期。

📦 Profile（配置档）

一叠有序的 bundle patch 层 + 用户覆盖，放在 ~/.dsh/profiles。dsh --profile <name> 启动。

🔌 Context（上下文）

Cordis 的服务容器 / 依赖注入层。插件在它上面 provide 与 inject 能力。

🧱 Bundle（捆绑包）

一个 npm 包，带 dsh.bundle.patch 指向 patch；被 Profile 列出后作为一个组合层生效。

🧩 Plugin（插件）

一个 Cordis 插件（name/apply/inject）。注册工具、提供服务、注入系统提示、技能或命令。

第一部分 · 概念

它们是怎么拼起来的（自底向上）

🧠 Agent
运行在 Runtime 上，使用 Context 里插件注册的 工具 / 系统提示 / 技能 / 命令。
▲ 运行于
⚙️ Runtime
把组合好的 Profile 实例化；构建并持有下面这棵 Context 树。
▲ 构建
🔌 Context
服务容器。Plugin 在其上 provide / inject：tools systemPrompt skills commands + 自定义服务。
▲ mount（apply）
🧩 Plugins
一条条 - id / name / config；每个插件在 Context 上注册能力。
▲ patch 插入
🧱 Bundles
每个 bundle 的 cordis.patch.yml 作为一层，插入若干 plugin 行。
▲ 列出
📦 Profile
dsh.profile.bundles 有序列出 bundles；再叠用户 patch。dsh --profile 启动。
第一部分 · 概念

Context 上的四类扩展点 + 自定义服务

🛠 tools

注册模型可调用的工具（含 JSON Schema 校验的输入输出）。本项目：get_market_snapshot 等 6 个。

📜 systemPrompt

往系统提示插入持久段落。本项目：guardrails 合规护栏。不注册任何工具也能改变行为。

📘 skills

注册可被模型/用户加载的技能规程。本项目：stock-research-pipeline。

⌨️ commands

注册斜杠命令。本项目：/research 把固定提示词作为新用户消息送入会话。

🧰 自定义服务（Service）—— 本项目的协作核心

research-run-store 提供 researchRunStore 服务：独占配置与 Python 桥。三个工具插件 inject 它，自己不持配置、不起进程。一个 run_id 由它串起五步。

第一部分 · 概念

Bundle 怎么“装进”运行时

加载链
  • Profile 启动：dsh --profile trading-research
  • Runtime 读 dsh.profile.bundles，按顺序叠加每个 bundle 的 patch 层
  • trading-bundle 的 patch 把七个 plugin 行 insert 进配置
  • 每个 plugin 的 apply(ctx) 在 Context 上 mount 自己的能力
两个容易混的“装入”
  • 插件：Profile 启动时由 bundle/patch 装入（配置层）
  • 文件系统 Skill .dsh/skills/…：由 dsh-base 自带的 skill-filesystem 在工作区指向本仓库时扫描装入
  • AGENTS.md：工作目录在本仓库时作为工作区指令进会话
所以演示前必须在 UI 里把工作区加到本仓库，否则磁盘 Skill 和 AGENTS.md 不进会话——这跟 bundle 装插件是两条独立通道。

第二部分

股票研究员的一天

真实的盘后研究，是一条可重复、可追溯的流水线，不是“让模型猜一只票”。

第二部分 · 角色

研究员在做什么，不做什么

研究员做的
  • 盘后复盘：先看整体市场环境（指数、涨跌家数）
  • 按写明的规则从股票池里选出候选，而不是凭感觉
  • 对候选做个股研究：价格、均线、动量、量能、距阶段高点
  • 做风险检查：数据是否完整、是否走弱、是否异常波动、是否扎堆
  • 落一份可复核的报告，写清数据日期、来源、缺失项
研究员不做的（合规边界）
  • 不下买入/卖出/目标价/仓位指令，只写观察条件
  • 不凭记忆补行情；数字必须来自可追溯的数据
  • 不把“没接入的数据”说成“暂无利空”
  • 候选为空就是结论，不改规则或日期去找更好看的结果
  • 不下单、不转账、不登录券商
这套边界后面会原样变成 guardrails 系统提示 和 AGENTS.md——角色约束先于任何一次提示词。
第二部分 · 流程

盘后研究流水线：六个动作

① 看市场
指数收在哪、涨跌家数、数据截止到哪天，决定进不进选股。
›
② 按规则选股
历史够、多头排列、涨幅适中、放量但不极端，取前 N 做候选。
›
③ 个股研究
把候选展开成研究卡，只摆事实，不补财务和新闻。
›
④ 风险检查
规则命中：缺数据移出重点，走弱/异常/扎堆/过期只警示。
›
⑤ 出报告
落 Markdown + JSON，写清日期、来源、缺失、免责。
关键特征：每一步的输入都来自上一步、口径一致；任一步失败就停在该步，不往下编。这正好对应 Harness 里“同一个 run_id 贯穿五步”。

第三部分 · 第 0 步

0触发：/research [demo]

输入
  • 用户在 UI 输入 /research，可选参数 demo（命令提示 input.hint="[demo]"）
  • rawInput 为空 → 默认 universe=demo
处理（command 插件）
  • 取 FIXED_PROMPT（shared/research-text.js）
  • 拼 …\nuniverse=demo。
  • agent.followup(createUserMessage(...)) 作为新用户消息送进会话
输出
  • 一句回执：“已按固定提示词开始盘后研究（universe=demo）”
  • 不碰行情、不调 Python——它只是“开工按钮”
如何衔接下一步
  • 固定提示词里写了“加载 daily-stock-research”
  • → 命中文件系统 Skill，引导 Agent 按五步调工具
// FIXED_PROMPT（节选）
加载 daily-stock-research。使用 fixture 数据，执行最近一个已冻结交易日的 A 股盘后研究。
只引用工具返回的数字。如果工具失败，停止并说明错误码。不要给出买卖指令。
第三部分 · 第 0.5 步

½Agent 读 Context：护栏 + 技能

systemPrompt：guardrails
  • 插件 apply() 时就把 GUARDRAILS 段插入系统提示
  • 内容：不给买卖/目标价 · 数字只来自工具 JSON · data_date 不是“今天” · 空字段≠“暂无利空” · 空候选是合法结果
  • 不注册任何工具，纯改行为
skills：stock-research-pipeline
  • 七步规程：快照失败即停、同一 run_id 贯穿、不研究候选外代码、摘要只复述观察条件
  • 与磁盘 daily-stock-research 分开命名避免互相遮蔽
于是 Agent 进入“研究员模式”：必须按固定顺序调五个工具，只复述 JSON 里的数字。 这一步没有 Python，只是上下文被插件改写过。
第三部分 · 衔接机制（贯穿五步）

一次工具调用，TS 怎么过桥到 Python

工具 execute()→ 注入的 store.xxx()→ runner 参数白名单校验→ spawn python→ CLI 子命令→ JSON 信封→ accept() schema 校验→ renderEnvelope → 模型 
// runner.js · runPython
spawn(python, ["-m", "trader.cli", ...command], {
  cwd: projectRoot, shell: false,
  env: { ...env, PYTHONPATH: projectRoot + "/python" }
});
// 超时 → SIGKILL → TIMEOUT 信封；stderr 落 data/logs/
// stdout 必须 JSON.parse 成对象，否则塌缩 INTERNAL 信封
要点：工具插件零配置、零进程；一切失败都收敛成标准信封，绝不把异常抛进 Agent 循环。参数白名单（universe、run_id 格式、symbols 1–5 只、limit 1–10）在 TS 侧先挡一道。
第三部分 · 第 1 步 · 看市场

1get_market_snapshot（真正的重计算）

输入
  • universe=demo（必填，枚举 demo/csi300）
  • as_of? 可选，默认用冻结样本日期，不许改日期“找好结果”
  • TS 侧执行 market-snapshot --universe demo --data-mode fixture --json
输出（data = market）
  • run_id = research-YYYYMMDD-HHMMSS
  • 指数点位、涨跌家数、data_date、warnings、source
内部真相：_snapshot 调 pipeline.run_daily，一口气做完：读 fixture → 校验日期 → 清洗日线 → 算 MA20/MA60/20日收益/量比 → screen() 选股 → 生成 run_id → save_run 落 SQLite → 顺带调 research/risk/report，连研报文件都写盘了。只是返回信封里只裁出 market。
衔接：把 run_id 交给 Agent。若 ok≠true，skill 规定立即停、只报 error.code，不进选股。
第三部分 · 第 2 步 · 按规则选股

2screen_stocks

输入
  • run_id（必填，来自第 1 步）
  • rule_set? 仅接受 trend_volume_v1
  • limit? 1–10（展示上限，TS 侧切片）
规则 trend_volume_v1
  • 历史≥60；close > ma20 > ma60（多头排列）
  • 20日收益 ∈ [5%, 40%]；量比 ∈ [1.2, 3.0]
  • 按涨幅排序取前 10 做候选
输出
  • candidates：symbol/name/industry/close/ma20/ma60/return_20d/volume_ratio/high_60d/distance_to_high_60d
  • candidate_count、eligible_count、excluded_counts、exclusions
  • 候选为空是合法结果（带 warning）
衔接：CLI screen 只 load_run 回读第 1 步已存的 screening，不重新加载行情、不改日期。规则阈值是可解释的演示规则，不是验证过的策略。
第三部分 · 第 3 步 · 个股研究

3get_stock_research_data

输入
  • run_id（必填）
  • symbols? 1–5 只本次候选（6 位、不重复）；省略则展开前 5 名
处理（build_cards）
  • load_bars+add_indicators 重建指标
  • 算 closes_above_ma20_ratio（近 20 日站上 MA20 比例）
输出：研究卡
  • 价格、均线、动量、量能、距 60 日高点
  • valuation / news / fund_flow 硬编码 null（未接数据源）
  • missing_fields、unavailable_fields
  • save_research 落库
合规衔接：空的三项是“未接入”，不是“暂无利空”；只摆候选内的事实，不写观点、不补财务新闻。
第三部分 · 第 4 步 · 风险检查

4check_stock_risk

输入 / 处理
  • run_id（必填），不传代码/路径
  • risk.checks.evaluate 逐候选 + 整体 run 跑规则
  • 若有候选却没先做研究卡 → 报 “先调用 get_stock_research_data”
输出：规则命中（非卖出建议）
  • 🔴 DATA_INCOMPLETE → block（移出重点）
  • 🟠 TREND_WEAKENING / ABNORMAL_MOVE
  • 🟠 INDUSTRY_CONCENTRATION（前5名同业≥3）
  • 🟠 STALE_SAMPLE（样本距今>5 天）
  • 产出 blocked_symbols / focus_symbols，save_risk
衔接：block 只表示“移出重点研究”，warn 不是卖出。focus_symbols 进下一步报告的重点段。
第三部分 · 第 5 步 · 出报告

5generate_daily_report

输入 / 处理
  • run_id（必填）
  • 从 SQLite 读回 run + cards + flags，组 context
  • reporting.render.write_report 渲染两份文件
输出
  • markdown_path / json_path：reports/<data_date>/<run_id>.md / .json
  • disclaimer、industry_distribution（候选分布，非板块排名）
  • focus_symbols / blocked_symbols
表格数字全部由 Python 生成，模型只能润色语言、不得改写数字。免责声明：仅用于演示研究流程，不构成投资建议、不触发任何交易。
收尾：Agent 按 skill 第 7 步向用户摘要 data_date、市场环境、候选、重点研究、风险命中——观察条件只复述规则失效，不写成委托。
第三部分 · 衔接的灵魂

一个 run_id 怎么把五步焊在一起

① snapshot 生成 run_id + 落库→ ② screen load_run→ ③ research load_run+save_research→ ④ risk load_risk/save_risk→ ⑤ report 读齐→渲染
为什么必须同一个 run_id
  • 重数据（读样本+指标+选股）只在第 1 步算一次，落 SQLite
  • 后面每步都是对同一份案卷的回读/补写，口径不会漂
  • 这就是护栏反复强调“同一 run_id、不另传日期”的技术原因
持久化落点
  • SQLite：data/trader.sqlite（runs / snapshots / screen_hits / bars / research / risk / report 表）
  • 人读副本：data/processed/<date>/<run_id>.json
  • 报告：reports/<date>/<run_id>.md / .json
第三部分 · 统一契约

每一步都返回同一个 JSON 信封

信封字段（contracts.envelope）
  • ok · tool · run_id · data_date
  • generated_at（上海时区）· source（provider/dataset/adjustment）
  • warnings[] · error{code,message,retryable} · data
两层校验
  • Python 侧：统一 envelope() / TraderError，错误码如 INVALID_ARGUMENT、DATA_QUALITY_FAILED、NO_CANDIDATES
  • TS 侧：accept(schema,...) 用 JSON Schema 校验；不符就塌缩成 INTERNAL 信封，不进 Agent 循环
// 失败也是合法信封，不抛异常
{ "ok": false, "tool": "screen_stocks", "run_id": null,
  "error": { "code": "INVALID_ARGUMENT", "message": "run_id 必须来自上一步…", "retryable": false },
  "data": null }
第三部分 · 失败与边界

任一步失败，系统怎么“停而不编”

🛑 快照失败

第 1 步 ok≠true → skill 要求停，只报 error.code，不进选股、不用记忆补行情。

⏱ Python 超时

runner 的 AbortController 到点 SIGKILL，丢弃不完整输出，回 TIMEOUT 信封（retryable）。

🧱 schema 不符

TS 的 accept() 校验失败 → INTERNAL 信封，绝不把坏数据喂给模型。

📭 空候选

合法结果：写明规则与样本范围，不改规则或日期重跑。

🚫 越界请求

guardrails + AGENTS.md：不下单/转账/登录券商，不输出买卖/目标价/仓位。

🗂 写盘失败

报告落盘 OSError → REPORT_WRITE_FAILED（retryable），带 run_id/data_date。

三道防线：Python 契约（envelope/TraderError）· TS 白名单+schema · 模型约束（guardrails/skill/AGENTS.md）。失败永远可见，不生成虚构行情。

设计取舍、验证与演示

第四部分 · 取舍

为什么是“插件 + 共享服务 + Python”

🐍 Python 计算，模型解释

清洗、指标、筛选、风险、回测都是确定性函数。模型不心算价格均线，只解释工具已返回的结构化结果。

🧰 服务是协作核心

三个工具插件零配置、零进程，统一 inject researchRunStore；一个 run_id 串全程，数字不会前后对不上。

🧩 四类扩展点各司其职

tools 暴露能力、systemPrompt 立规矩、skills 给手册、commands 做开工按钮。拆成七个包演示“插件不只是注册工具”。

🧱 Bundle 一层装好

七个插件由一个 bundle 作为组合层装进 Profile；Profile 只 link 这一个 bundle，升级/复用干净。

没有 workflow.yaml：业务工作流由 Profile + 插件 + AGENTS.md + Skill 共同定义，确定性计算绝不交给模型即兴写 JS。

怎么证明它真的跑通
