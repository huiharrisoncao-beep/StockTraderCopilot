第一部分 · 回顾

六个概念，一句话各讲清

🧠 Agent（智能体）

按一轮轮循环工作：决定调哪个工具、读系统提示、按需加载技能。它不写死能力，而是用 Runtime 给的那一套。

⚙️ Runtime（运行时）

把组合好的 Profile 实例化出来的运行环境：一棵 Cordis Context 树 + 生命周期，承载组装后的能力。

📦 Profile（配置档）

一叠有序的 bundle patch 层 + 你自己的覆盖，放在 ~/.dsh/profiles。dsh --profile <name> 启动它。

🔌 Context（上下文）

Cordis 的服务容器 / 依赖注入层。插件在它上面 provide 和 inject 服务：tools、systemPrompt、skills、commands，及自定义服务。

🧱 Bundle（捆绑包）

一个 npm 包，带 dsh.bundle.patch 指向 patch 文件；被 Profile 的 bundles 列出后，作为一个组合层生效。

🧩 Plugin（插件）

一个 Cordis 插件（name / apply / inject）。在 Context 上注册工具、提供服务、注入系统提示、技能或命令。

第二部分 · 实践

每个插件具体完成什么

插件实际工作
run-store持有唯一配置（Python 路径、fixture/live、120 秒超时）。提供 researchRunStore，把五步调用转成 trader.cli：market-snapshot / screen / stock-research / check-risk / report。不注册工具。
market-dataping_research 只做健康检查，不读行情。get_market_snapshot 读取冻结样本，写出 run_id、指数、涨跌家数、data_date 和 warnings，schema 校验通过后才交给模型。
screening只接受已有 run_id。按 trend_volume_v1 读出候选（可限 1–10 只）。候选为空是合法结果；不另传日期，也不改规则重跑。
research-report三件事：把前 5 名展开成研究卡（估值 / 新闻 / 资金流固定为空）；检查规则命中，block 移出重点、warn 不是卖出；把这次 run 渲染成 Markdown 和 JSON。
guardrails不加工具。在系统提示里插入 stock-research:guardrails：禁止买卖指令和目标价；数字只能引用工具 JSON；data_date 不是“今天”；空字段不是“暂无利空”。
skill注册 stock-research-pipeline（模型和用户都可调用）。内容是七步规程：快照失败即停，同一 run_id 贯穿，不研究候选外的代码，摘要只复述观察条件。与磁盘上的 daily-stock-research 分开，避免被挡住。
command注册 /research。把固定提示词作为一条新的用户消息送进当前会话，universe 默认 demo。回执写明：只引用工具数字，不给买卖指令。

三个工具插件自己不读配置、不起 Python。计算都进 run-store，再由 Python 写入同一份 SQLite。

第二部分 · 实践

每个插件完成的业务

插件研究员工作里的那一段
run-store一次盘后研究的案卷。开案时记下数据模式和截止日；选股、个股、风险、报告都读同一份档案，避免前后数字对不上。
market-data先看市场。确认样本截止哪一天、指数收在哪里、涨跌家数如何，再决定进不进选股。健康检查不算研究。
screening按写明的规则选股，不是模型挑票。历史够、多头排列、20 日涨幅落在区间、放量但不极端。按涨幅取前 10 做候选；没有票也是结论。
research-report研究收尾三段：个股卡只摆事实（价格、均线、动量、量能、距阶段高点），不写观点、不补财务和新闻；风险只报规则命中，数据缺失就移出重点，走弱、异常波动、行业扎堆、样本过期只警示；最后落一份可复核的盘后报告。
guardrails职业边界。可以写观察条件，不能下买卖指令、目标价或仓位；没接到的数据不能说成“暂无利空”；空候选不能改规则再找一只更好看的。
skill作业手册。用户说盘后研究、每日研究或选股报告时，按固定顺序做完；某步失败就停；摘要只复述工具里的数字和观察条件。
command开工按钮。一句 /research 按当天规程开始这次盘后研究，默认用演示股票池。

业务上是一条研究流水线。插件把每一段职责装进 Harness；模型负责解释，不负责算数和下单。

不是工具的插件，才体现“广度”

🛡️ guardrails

往 系统提示注入一段护栏：不给买卖指令、只引用工具 JSON、data_date 不是“今天”。塑造 Agent 行为，不加任何工具。

📚 skill

从插件内注册 stock-research-pipeline 技能，装插件即带流程说明——不依赖磁盘上的 .dsh/skills。

⌨️ command

给 UI 加 /research，用 invocation.agent.followup 注入一条用户消息，一键按固定提示词发起研究。

四类扩展点各来一个，说明同一套插件机制能从工具、服务、提示、技能、命令多个维度扩展 Harness。
第二部分 · 实践

合规与可追溯是设计的一部分

模型被约束在数据里

  • 价格、指标、筛选只能来自工具 JSON
  • valuation / news / fund_flow 留空＝未接入，不是“暂无利空”
  • 候选为空是合法结果，不强行推荐
  • 只写“观察条件”，不生成委托

两份留痕都写

  • 给人看：reports/<date>/<run_id>.md 与 .json
  • 可追溯：data/trader.sqlite（runs / 候选 / 研究卡 / 风险 / 报告）
  • 报告末尾固定免责声明：仅演示研究流程，不构成投资建议
范围边界：不接券商、不下单、不转账、不实时盯盘。这是研究流程平台，不是自动交易机器人。

第三部分 · 收尾

一路上的设计取舍

为什么拆成七个插件

演示主题是“插件”。拆分让服务协作和多扩展点在目录与 dump-config 上一眼可见；共享代码收在一个 lib 包里。

为什么用 bundle 加载

bundle 是 DSH 正规的组合层机制；一行 bundles 就把七个插件作为一层装好，而不是堆用户 patch。

为什么 Python 算、模型解释

数字可复核、可离线、可重复；模型发挥也不会污染计算层。表与文本不一致时以表为准。

为什么服务只在 run-store

配置与 Python 桥集中一处；工具插件零配置，一个 run_id 天然贯穿同一份 SQLite。
